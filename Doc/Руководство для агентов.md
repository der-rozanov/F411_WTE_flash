# Руководство для агентов: испытательный стенд на Matek F411-WTE

Этот документ для ИИ-агентов, которые вместе с владельцем разрабатывают испытательный стенд и собственную прошивку полётного контроллера на плате Matek F411-WTE. Прочитай его целиком до первой правки кода.

Всё о плате (распиновка, тактирование, настройки CubeMX, загрузчик) — в соседнем файле [Matek F411-WTE как плата разработки.md](Matek%20F411-WTE%20как%20плата%20разработки.md). Здесь — как работать.

## 1. Цель проекта

- **Сейчас:** испытательный стенд. Плата лежит на столе, подключена по USB. Через терминал на COM-порту можно опросить каждый датчик, подвигать каждый выход и увидеть результат.
- **Дальше:** собственная прошивка полётного контроллера на той же базе.
- Стенд — фундамент прошивки. Драйверы, которые пишутся для стенда, потом переиспользуются в полётном коде. Поэтому они должны быть аккуратными с первого дня.

## 2. Главное правило: код читает человек

Владелец должен открыть любой файл и понять, что он делает, без даташита на столе. Это важнее краткости и важнее «как принято в embedded».

### Что это значит на практике

1. **HAL, а не регистры.** Пиши через функции STM32 HAL (`HAL_GPIO_WritePin`, `HAL_SPI_TransmitReceive`, `HAL_TIM_PWM_Start`). Прямая запись в регистры (`GPIOA->ODR |= ...`, `RCC->APB1ENR`) — только если в HAL этого нет. Такое место прячется в маленькую функцию с понятным именем и комментарием «почему не HAL». Пример в проекте: переход в загрузчик в `bootloader.c`.
2. **Регистры датчиков — по именам.** Адреса и биты регистров чипов (гироскоп, барометр, OSD) объявляются именованными константами в начале драйвера, с комментарием из даташита. В коде никаких `0x75`, `0x80`, `0x0F` посреди строки.
3. **Единицы измерения в именах.** `pulse_us`, `voltage_mv`, `current_ma`, `period_ms`, `pressure_pa`, `rate_hz`. Читатель не должен гадать, это миллисекунды или такты.
4. **Никаких магических чисел.** Любое число, кроме 0 и 1, получает имя: `#define SERVO_CENTER_US 1500`, `#define VBAT_DIVIDER 11`.
5. **Короткие функции с одной задачей.** Функция помещается на экран. Имя говорит, что она делает: `imu_read_gyro()`, `power_read_battery_mv()`, `outputs_set_servo_us()`.
6. **Понятные имена, без сокращений-загадок.** `battery_voltage_mv`, а не `bv`; `imu_init`, а не `ii`. Общепринятые сокращения (IMU, ADC, PWM, CS, SPI) — можно.
7. **Комментарии на русском, объясняют «зачем», а не «что».** Плохо: `// установить пин`. Хорошо: `// CS вниз: с этого момента гироскоп слушает шину`.
8. **Без хитростей.** Никаких битовых трюков ради экономии пары тактов, макросов-монстров, указателей на функции там, где хватает `if`. Если хитрость действительно нужна — комментарий, почему.
9. **Проверка ошибок.** Функции, которые общаются с железом, возвращают результат (`bool` или код ошибки), и вызывающий его проверяет. Молча проглатывать `HAL_ERROR` нельзя.

### Пример: так нельзя

```c
uint8_t b = 0x75 | 0x80;
GPIOC->BSRR = (1 << 29);
HAL_SPI_TransmitReceive(&hspi2, &b, &r, 2, 10);
GPIOC->BSRR = (1 << 13);
if (r[1] != 0x47) e |= 4;
```

### Пример: так надо

```c
/* ICM42688P: регистры и значения из даташита, раздел 14 */
#define ICM42688_REG_WHO_AM_I    0x75u
#define ICM42688_WHO_AM_I_VALUE  0x47u
#define SPI_READ_FLAG            0x80u  /* старший бит адреса = чтение */
#define SPI_TIMEOUT_MS           10u

/* Прочитать один регистр гироскопа по SPI2 */
static bool imu_read_register(uint8_t reg, uint8_t *value)
{
  uint8_t tx[2] = { reg | SPI_READ_FLAG, 0x00 };
  uint8_t rx[2] = { 0 };

  HAL_GPIO_WritePin(IMU_CS_GPIO_Port, IMU_CS_Pin, GPIO_PIN_RESET);  /* выбрать гироскоп */
  HAL_StatusTypeDef status = HAL_SPI_TransmitReceive(&hspi2, tx, rx, sizeof(tx), SPI_TIMEOUT_MS);
  HAL_GPIO_WritePin(IMU_CS_GPIO_Port, IMU_CS_Pin, GPIO_PIN_SET);    /* отпустить шину */

  *value = rx[1];
  return status == HAL_OK;
}

/* Гироскоп на месте, если он ответил своим идентификатором */
bool imu_is_present(void)
{
  uint8_t who_am_i = 0;
  return imu_read_register(ICM42688_REG_WHO_AM_I, &who_am_i)
      && who_am_i == ICM42688_WHO_AM_I_VALUE;
}
```

## 3. Работа с CubeMX: кто что делает

- **`.ioc` — единственный источник правды** о пинах, тактировании и периферии. Его настраивает и генерирует **владелец**, сам, в CubeMX.
- Агент **не правит `.ioc` вручную** и не запускает генерацию без явной просьбы. Если нужна новая периферия или другая настройка — агент пишет владельцу точные шаги: где в CubeMX щёлкнуть, какое поле и какое значение поставить, как проверить результат в сгенерированном коде. Владелец делает и сообщает.
- **Свой код в сгенерированных файлах — только между `/* USER CODE BEGIN ... */` и `/* USER CODE END ... */`.** Всё вне этих секций CubeMX сотрёт при следующей генерации.
- **Новый код — в новых файлах**, а не в `main.c`. `main.c` только вызывает инициализацию модулей и их функции в главном цикле.
- После генерации владельцем агент перечитывает изменённые файлы (`.ioc`, `main.c`, `*_it.c`, файлы периферии) и проверяет, что пины и параметры совпадают с документом о плате.

## 4. Структура кода стенда

Новые файлы кладутся в `Core/Src` и `Core/Inc` с префиксом по слою. Эти папки уже в путях сборки, CubeMX чужие файлы в них не трогает.

| Слой | Префикс | Что внутри | Пример |
| --- | --- | --- | --- |
| Плата | `board` | имена пинов и констант платы, перевод сырых значений в единицы | `board.h`: `VBAT_DIVIDER`, `CURRENT_MV_PER_AMP` |
| Драйверы | `drv_` | один файл на одно устройство, ничего не знает о стенде | `drv_icm42688.c`, `drv_spl06.c`, `drv_at7456.c`, `drv_power.c`, `drv_outputs.c`, `drv_beeper.c` |
| Сервисы | `svc_` | общее: консоль на USB, вывод текста, планировщик | `svc_console.c`, `svc_scheduler.c` |
| Стенд | `bench_` | команды и режимы стенда, собирает всё вместе | `bench_commands.c` |

Правила зависимостей: стенд → сервисы и драйверы → HAL. Драйвер не вызывает консоль и не печатает сам. Он возвращает данные, печатает стенд.

Уже есть и трогать без нужды не надо: `bootloader.c/.h` (переход в DFU), доработки в `USB_DEVICE/App/usbd_cdc_if.c`.

## 5. Главный цикл и время

- **Главный цикл не блокируется.** Никаких `HAL_Delay` дольше нескольких миллисекунд в цикле. Периодические задачи — по `HAL_GetTick()`: «прошло 100 мс → прочитать датчик».
- В каждом проходе цикла обязательно вызывается `Bootloader_Poll()`. Без него перестанет работать прошивка без кнопки.
- В прерываниях (включая обработчики USB) — минимум работы: положить данные в буфер, поставить флаг. Разбор команд и печать — в главном цикле.
- `CDC_Transmit_FS()` возвращает `USBD_BUSY`, если прошлая передача не закончилась. Вывод в консоль идёт через буфер в `svc_console`, а не прямыми вызовами откуда попало.

## 6. Консоль стенда

Стенд управляется текстовыми командами через USB COM-порт (115200, любой терминал). Предлагаемый набор, расширяется по ходу:

| Команда | Что делает |
| --- | --- |
| `help` | список команд |
| `status` | всё сразу: какие датчики найдены, напряжение, ток, время работы |
| `imu` | ID гироскопа и текущие показания гироскопа/акселерометра в единицах (°/с, g) |
| `baro` | ID барометра, давление (Па), температура (°C) |
| `power` | напряжение батареи (мВ), ток (мА), RSSI и датчик скорости (мВ) |
| `servo <1-6> <мкс>` | импульс на выходе S1–S6 |
| `arm` / `disarm` | разрешить или запретить выходы моторов S1/S2 |
| `beep <мс>` | пищалка |
| `vbat on/off`, `cam 1/2` | ключи PINIO |
| `i2c scan` | список адресов на шине I2C1 |
| `dfu` | переход в загрузчик (уже работает) |

Ответы — человекочитаемые строки с единицами: `battery: 11.84 V, current: 0.42 A`, а не сырые числа АЦП.

## 7. Безопасность железа

На выходы S1/S2 могут быть подключены регуляторы с моторами. Ошибка в коде = раскрученный мотор на столе.

- **Пропеллеры снимаются всегда.** Агент напоминает об этом перед любыми опытами с моторами.
- **Выходы моторов после старта — в безопасном состоянии:** ШИМ 1000 мкс (стоп) или выключен. Никогда не запускать моторы в коде по умолчанию.
- **Моторы — только после явной команды `arm`**, с ограничением максимального импульса на время испытаний и автоматическим `disarm` по таймауту без команд.
- **Перед действиями, которые двигают железо или включают питание** (моторы, сервы с нагрузкой, ключ Vbat на VTX/камеру), агент спрашивает владельца, что подключено, и ждёт ответа.
- При питании только от USB шина 5 В на пятаках не запитана (так у этой платы). Для серв и регуляторов нужна батарея.

## 8. Сборка, прошивка, проверка

- **Сборка.** Если CubeIDE открыта, её workspace заблокирован. Агент собирает копию проекта во временном workspace:
  ```
  "C:\ST\STM32CubeIDE_1.12.0\STM32CubeIDE\stm32cubeidec.exe" --launcher.suppressErrors -nosplash -application org.eclipse.cdt.managedbuilder.core.headlessbuild -data <временная папка>\.ws -import <копия проекта> -build F411CEU6/Debug
  ```
  Цель — 0 ошибок и 0 предупреждений. Предупреждения не игнорируются.
- **Прошивка.** `F411CEU6\flash_dfu.bat [путь к .elf]`. Кнопка не нужна, пока работает наша прошивка. Перед прошивкой закрыть терминал на COM-порту.
- **Отладчика нет.** Светодиоды сидят на пинах SWD (PA13/PA14), ST-Link не подключить. Отладка — выводом в USB-консоль и светодиодами.
- **Проверка на железе.** После прошивки агент открывает COM-порт, отправляет команды и смотрит ответы. В отчёте владельцу честно разделяет: что проверено на плате, что только собрано, что не проверено вовсе.
- **Если плата перестала отвечать по USB** — это не «кирпич». Зажать кнопку на плате, переподключить USB, прошить рабочую версию.

## 9. Документация

Документация — часть работы, а не задача «на потом». Изменение без обновлённой документации не считается законченным.

- **Где.** Вся документация — в папке `Doc` рядом с проектом, Markdown, на русском.
- **Файл о плате** (`Matek F411-WTE как плата разработки.md`) обновляется, когда подтверждается или опровергается факт о железе: адрес барометра, активный уровень PINIO, ориентация гироскопа. Рядом с фактом — как он проверен.
- **Один файл на модуль**, когда модуль готов: `Doc/drv_icm42688.md` — что делает, как подключён, какие функции, как проверить, известные ограничения.
- **Журнал изменений** `Doc/Журнал.md`: дата, что сделано, что проверено на плате. Новые записи сверху.
- **Комментарий-шапка в каждом новом `.c`-файле:** что это за модуль, с каким железом работает, ссылка на даташит.
- **Стиль текста.** Коротко, по делу, без воды. Числа с единицами. Сначала главное, потом детали.

## 10. Как общаться с владельцем

- Язык — русский, простыми словами. Термин, который может быть непонятен, — пояснить при первом упоминании.
- Владелец сам работает в CubeMX и сам нажимает кнопки на плате. Инструкции для него — пошаговые: какое меню, какое поле, какое значение, как проверить.
- Перед крупной работой — коротко план. После — что сделано, что проверено, что осталось.
- Неуверенность — говорить прямо: «предположение, проверим на плате», а не выдавать догадку за факт.

## 11. Открытые вопросы (на 22.10.2026)

- [ ] **SPI2 Prescaler** в `.ioc` стоит /2 (24 Мбит/с) — нужно /8. Владелец правит сам.
- [ ] **TIM3 Prescaler** в `.ioc` стоит 0 — нужно 95, иначе S3–S6 на 4,8 кГц вместо 50 Гц. Владелец правит сам.
- [ ] Какой гироскоп на этой плате: ICM42688P или BMI270 — проверить чтением ID.
- [ ] Адрес барометра SPL06-001 на I2C: 0x76 или 0x77 — проверить сканом шины.
- [ ] Активный уровень ключей PINIO (PC15 Vbat, PB10 камера) — проверить мультиметром.
- [ ] Активный уровень светодиодов (горят от High или от Low) — не важно для мигалки, важно для индикации состояний.
